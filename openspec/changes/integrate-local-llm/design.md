## Context

本项目是一个 Android + Flutter 混合应用，使用 Flutter Engine Group 实现原生与 Flutter 页面跳转。当前 Flutter 模块仅实现了页面导航演示，缺少核心功能。目标是在 Flutter 模块中集成端侧 LLM 能力，让应用能在设备本地运行大语言模型，实现聊天对话。

技术约束：
- Android 项目使用 Gradle 8.14 / AGP 8.11.1 / Kotlin 2.1.10，compileSdk 36 / minSdk 24 / targetSdk 36
- Flutter SDK ^3.12.0
- 使用阿里云 Maven 镜像
- 原生层只做"模型推理"，业务逻辑全部在 Dart 层

## Goals / Non-Goals

**Goals:**
- 在 Android 端编译并集成 llama.cpp 原生库（arm64-v8a）
- 通过 Dart FFI 绑定 llama.cpp 的 C API，提供模型加载和文本生成能力
- 实现聊天对话服务，支持多轮对话历史管理和流式输出
- 提供基础的聊天 UI（消息气泡、输入框、加载状态）
- 支持模型文件下载和本地管理
- 实现最小可运行的 Demo：加载模型 → 输入消息 → 获得回复

**Non-Goals:**
- iOS 和桌面端支持（当前阶段仅 Android）
- Function Call / 工具调用
- 多 Agent 编排
- 多模态（图像理解）
- 模型热切换
- GPU/NPU 加速（先用 CPU 推理保证通用性）
- 生产级错误处理和边界情况覆盖

## Decisions

### 1. 选择 llama.cpp + 自封装 FFI 而非现成插件

**决策**：基于 llama.cpp 的 C API，自己写 Dart FFI 绑定。

**理由**：
- pub.dev 上的端侧 LLM 包（如 llama_cpp_dart）均处于实验阶段，维护状态不稳定
- llama.cpp 的 C API 简洁，核心函数仅 5-6 个，自封装工作量可控（1-2 天）
- 获得完全的控制权：版本、功能、各平台库版本均可控
- 完整理解 FFI 链路，对后续维护有帮助

**替代方案**：使用 llama_cpp_dart 插件。放弃原因：维护不稳定，版本滞后，发现问题难以快速修复。

### 2. 选择 GGUF 格式和 Qwen 2.5 0.5B 模型作为初始验证

**决策**：使用 GGUF 格式模型，初始验证用 Qwen 2.5 0.5B Instruct Q4_0。

**理由**：
- GGUF 是 llama.cpp 的原生格式，单文件、已量化、即插即用
- Qwen 2.5 0.5B 约 350MB，内存占用约 500MB，对低端手机友好
- 中文能力可用，商用许可允许商用
- 先验证链路跑通，再考虑换更大的模型

**替代方案**：MLC 编译方案。放弃原因：需要预编译，换模型要重新编译，灵活性差，更适合固定模型的生产场景。

### 3. 原生层最小化，Dart 层最大化

**决策**：原生 Android 层只做模型推理，所有业务逻辑（对话管理、消息格式化、状态管理）都在 Dart 层实现。

**理由**：
- 符合项目"原生只是一个壳子"的设计哲学
- Dart 代码可跨平台复用，未来扩展到 iOS/桌面端时代码可复用
- 业务逻辑迭代不需要重新编译原生库

### 4. 先 CPU 推理，后考虑 GPU 加速

**决策**：第一阶段使用 llama.cpp 的 CPU 多线程推理，不启用 GPU/Vulkan。

**理由**：
- CPU 推理兼容性最好，所有 Android 设备都能跑
- 0.5B 模型在 CPU 上速度足够（60-100 tok/s）
- GPU 加速需要额外的编译配置和驱动兼容处理，增加复杂度
- 可作为后续优化方向

### 5. 使用 Riverpod 进行 Dart 层状态管理

**决策**：使用 Riverpod 管理聊天状态、模型加载状态、生成状态。

**理由**：
- Riverpod 是 Flutter 社区推荐的状态管理方案，类型安全、测试友好
- 适合管理复杂的异步状态（模型加载、流式生成）
- 与现有 Flutter 模块兼容

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|---------|
| 低端手机内存不足导致 OOM | 使用 0.5B 小模型，提供内存检测和友好提示，后续可支持模型大小选择 |
| FFI 绑定存在内存泄漏风险 | 仔细管理 Pointer 生命周期，使用 `calloc`/`malloc` 对应 `free`，提供 `dispose()` 方法 |
| 首次模型下载体积大（350MB+） | 在 UI 中明确提示，支持下载进度显示，考虑后续支持模型压缩包或分片下载 |
| llama.cpp API 版本升级导致绑定失效 | 锁定 llama.cpp 版本，升级时同步更新 FFI 绑定 |
| 构建系统复杂度增加（CMake + NDK） | 提供详细的构建文档，将 CMake 配置纳入 Gradle 构建流程 |
| 中文 tokenization 可能存在边界问题 | 使用与模型配套的 chat template，测试中文输入输出 |

## Migration Plan

本变更属于新增功能，不涉及现有代码迁移。

部署步骤：
1. 合并代码后，首次构建会自动触发 CMake 编译 libllama.so
2. 用户在应用内首次进入聊天页面时，触发模型下载（如果本地无模型）
3. 模型下载完成后自动加载，加载成功即可开始对话

## Open Questions

1. 模型文件存储在应用私有目录还是外部存储？（倾向于私有目录，保护模型文件）
2. 是否需要在应用启动时预加载模型？（倾向于按需加载，减少启动内存占用）
3. 对话历史是否需要持久化存储？（Phase 1 不持久化，仅内存中维护）
